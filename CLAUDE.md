# CLAUDE.md — DITSALA

Working notes for whoever (human or Claude) picks up this repo next. Full detail lives in `docs/DITSALA_MASTER_SPEC.md` (v1.0, finalized) — this file is the fast-orientation summary, kept current as phases complete.

## Current phase

**Phase 0 — Foundation: complete.** Monorepo tooling (pnpm + Turborepo, uv for the backend), `docker-compose.yml` (Postgres/Redis/coturn/Mailpit), CI (GitHub Actions: lint/type-check/test for both the TS workspace and the backend), `packages/ui-tokens` (Ditsala palette + type scale), backend skeleton with a working `/api/v1/health` endpoint, and the first Alembic migration (`pgcrypto` extension) are in place.

**Phase 1 — Data model: complete.** All 34 tables from spec §4 as Alembic migrations (`631a559a0977` core schema + `1bcfa1c65e5e` classification/RLS), SQLAlchemy models for every table (`backend/app/models/`), the §5 data-classification registry as its own module (`backend/app/domain/classification.py`), four Postgres DB roles (`app_backend`, `app_admin_readonly`, `app_admin_kyc_reviewer`, `app_maintenance`) with column-level grants matching P0-P3 classification, and RLS policies on `messages`/`conversation_members`/`location_shares`/`location_pings` — all proven against a real Postgres via integration tests, not just declared. A full repository layer (`backend/app/repositories/`) covers every aggregate.

**Phase 2 — Onboarding & identity: backend complete, mobile screens not yet started.** `EmailProvider` (Resend real + `SandboxEmailProvider` over local SMTP), `OtpProvider` (Twilio Verify real + sandbox-credential variant), `KycProvider` (Smile ID real + sandbox-host variant) — all behind `domain/onboarding/interfaces.py`, selected only via `services/factory.py` reading env vars. `domain/onboarding/service.py` implements the full §14 state machine up to `pending_code` (device+key registration to reach `active` is Phase 3's job, deliberately not built here). API routes under `/api/v1/onboarding/*` plus a Smile ID webhook endpoint, gated by a short-lived onboarding JWT rather than a raw user id in the URL (see ADR 0002 — avoids an IDOR in the pre-auth part of the flow). Argon2id for the DITSALA Code and email codes, a separate deterministic HMAC hash for `national_id_hash` (see ADR 0002 for why Argon2id would silently break the uniqueness constraint there).

31 backend tests pass, including a real one: `SandboxEmailProvider` was verified against an actual running Mailpit instance (SMTP delivery + API-confirmed receipt), not just code review. Twilio Verify and Smile ID adapters are code-complete but **not live-verified** — no vendor account exists in this environment; see `docs/SECURITY_GAPS.md` for the Smile ID field-accuracy caveat specifically.

**Mobile**: `apps/mobile` is a real Expo Router + NativeWind app (Expo SDK 57), not a stub — scaffolded via `create-expo-app`, joined into the pnpm workspace (see ADR 0003 for the `node-linker=hoisted` + Metro symlink config that took to make that work with React Native), consuming `@ditsala/ui-tokens` for its dark/gold palette. Full onboarding screen flow wired to the real backend API: welcome → signup → verify-email → verify-phone → kyc-document → kyc-liveness → next-of-kin → set-code → complete. The DITSALA app icon (`docs/brand/`) is wired in for iOS, Android (adaptive + monochrome), and web favicon.

**Known mobile gap** (ADR 0003): the KYC screens request real backend jobs/tokens but have no native capture UI — the Smile ID mobile SDK needs a config plugin and native iOS/Android build tooling (Xcode, Android Studio, EAS) this environment doesn't have. A user cannot progress past `pending_kyc_document` through the app UI alone yet. Not a security gap (no control is weakened) — a feature-completeness one, for whoever picks up the native SDK integration next.

**Not runtime-verified**: no simulator, physical device, or EAS build was available to actually launch the app. Verified: `tsc --noEmit`, ESLint, and Jest (16 tests: validation logic, the onboarding context, `Button`/`TextField`) all pass — including `Button`/`TextField` importing colors from `@ditsala/ui-tokens` directly, which confirms the pnpm workspace symlink + `node-linker=hoisted` + Metro `unstable_enableSymlinks` setup (ADR 0003) resolves correctly through the type-checker, linter, and Jest's module resolution. What's still unverified is Metro's own bundler at actual `expo start`/EAS-build time — smoke-test that on a machine with Xcode/Android Studio before trusting this further.

Not yet built in Phase 2: the breach-corpus check for the DITSALA Code (`docs/SECURITY_GAPS.md`).

**Phase 3 — Authentication & Sessions: complete (backend + mobile).** `domain/auth/service.py` (`AuthService`) owns the `pending_code` → `active` transition (device registration completes onboarding — Signal key upload itself is Phase 4's job) and two-factor login (§17): `POST /auth/login/start` (DITSALA Code) → Smile ID SmartSelfie liveness job → webhook lands the result → `POST /auth/login/complete` (checked within a 15-minute validity window). One uniform login flow handles every full-auth event (new device, after logout, recovery-adjacent) — there is no "trusted device, code only" server path, per §17.

Stateless short-lived access JWTs (`ACCESS_TOKEN_TTL_MINUTES`) + stateful rotating refresh tokens (`POST /auth/refresh`) with reuse detection — replaying an already-rotated-away refresh token revokes the entire session family, not just that token (see ADR 0004 for the full session model and the deliberate access-token revocation-latency tradeoff this implies). Device registry (`GET /auth/devices`, `DELETE /auth/devices/{id}`), `POST /auth/logout` (one session) and `/auth/logout-all` (every session), code-attempt lockout with escalating duration, and login-attempt logging are all in place.

A real Phase 2 bug was found and fixed while building this: `OnboardingService.start_kyc_liveness` never pre-created the `KycFaceVerification` row the webhook router's user-lookup depends on — see ADR 0004. 48 backend tests pass total (11 new domain tests, 5 new API tests for Phase 3). The Smile ID webhook HTTP endpoint's signature verification still has no test with a real payload (`docs/SECURITY_GAPS.md`) — same vendor-account limitation as Phase 2.

**Phase 3 mobile: complete.** `lib/session.ts` (SecureStore-backed access/refresh token storage) and `lib/biometric.ts` (expo-local-authentication) implement routine unlock exactly as §17 describes it: the biometric prompt never leaves the device and only gates access to the stored refresh token — the actual server call is a plain `/auth/refresh`, never a fresh authentication. `app/index.tsx` now checks for a stored session on launch and offers "Unlock" (biometric + refresh) instead of "Get Started" when one exists, falling back to a full login if the refresh token was rejected. `app/login.tsx` implements the full two-factor flow (code, then liveness-check polling) for new devices/after logout. `app/onboarding/complete.tsx` now actually calls `/auth/complete-onboarding` instead of just displaying state. `app/home.tsx` is a placeholder authenticated screen (Phase 4+ builds the real app) that exercises the device registry and logout/logout-everywhere end to end.

25 mobile tests pass (9 new: session storage and biometric-gating logic, both with the native modules mocked — `jest.mock` factories needed their captured variables renamed to a `mock`-prefixed convention, a real Jest/babel hoisting restriction hit while writing these). Same runtime-verification boundary as the rest of Phase 2/3 mobile: `tsc`/ESLint/Jest all pass; nothing has been launched on a simulator/device.

**Phase 4 — E2EE Messaging: backend complete; mobile now has a real chat UI (ADR 0013 superseded the original libsignal plan).** The backend's role is inherently crypto-agnostic (it stores/relays public key material and opaque ciphertext, never decrypts, by design per §7.3), so `domain/messaging/service.py` and the `/api/v1/messaging/*` REST + WebSocket routes are real, fully tested, production-shaped code: key registration (identity key, signed prekeys with rotation, one-time prekeys with consume-once semantics), prekey-bundle retrieval, 1:1 and group conversations (with a real `title` for groups now, gated by the same Circle-tier check `start_direct_conversation` already had), message send/list/edit/delete with idempotency via `client_message_id`, delivery/read receipts, disappearing messages (`purge_expired_messages`, scheduled since Phase 8), pin/mute/archive, media (presigned S3/MinIO-compatible upload/download via `StorageProvider`), block/unblock, an in-memory `ConnectionManager` for realtime WebSocket delivery, and a `GET .../members` endpoint (enriched with `display_name`/`avatar_url`).

**libsignal itself remains unbuilt** (see `docs/adr/0005-e2ee-native-module-gap.md`) — real Kotlin/Swift native-module engineering, weeks of work, verifiable only via a real device/EAS build this environment never had. Per **ADR 0013**, the user explicitly chose to stop waiting on it: the client-side crypto is now **TweetNaCl** (X25519 identity + Ed25519-signed prekeys + XSalsa20-Poly1305, a session-less per-message "X3DH-lite" for 1:1, Sender Keys for groups) — real, audited primitives, fully unit-tested (`apps/mobile/lib/crypto/*.test.ts`, 21 tests covering key generation, encrypt/decrypt round trips, tampering rejection, and impostor-identity rejection — something the native-libsignal path could never be tested at all in this environment). `react-native-quick-crypto` was evaluated as a faster native alternative and deliberately deferred (loses Jest-testability entirely, no NaCl-secretbox equivalent in Node's crypto API) — see the ADR's addendum.

**Sender Keys now unify direct and group messaging, with real multi-device fan-out** (superseding the original "one device per recipient" V1 limitation): every conversation — 1:1 or group — uses the same Sender Key mechanism (`apps/mobile/lib/crypto/chat-crypto.ts`), distributed to *every* device of *every* member via `GET /messaging/keys/devices/{user_id}` (`IdentityKeyRepository.list_for_user`) rather than just a "primary" device. This surfaced a real, pre-existing schema bug: `SenderKey` originally held one shared blob per sender, which can't actually hold N different per-recipient ciphertexts — fixed by adding a `recipient_device_id` column (migration `45bfe2c8fef5`) so each recipient device gets its own distribution ciphertext.

**Real chat UI now ships**: `apps/mobile/app/messages/` (conversation list with avatars/last-activity, a chat screen with real send/receive, decrypt-on-read, realtime updates via the existing WebSocket), wired from a new "Message" button on Circle's verified/trusted contacts. `lib/crypto/keystore.ts` (key persistence in `expo-secure-store` + backend registration/replenishment), `chat-crypto.ts` (the high-level encrypt/decrypt orchestration screens actually call), and `wire.ts` (envelope-to-bytes encoding for the single opaque `ciphertext` field) sit between the crypto primitives and the UI. **Not yet built**: a local offline cache (design already decided — ciphertext-only in `expo-sqlite`, decrypt in memory, no SQLCipher — see ADR 0013), media/image messages in the UI (the crypto support already exists, untested from a screen), and a group-creation UI screen (the backend's Circle-tier gate exists; no mobile screen calls it yet) — see `docs/SECURITY_GAPS.md`.

**Also new this pass**: profile pictures (`User.avatar_key`, reusing the same presigned-URL `StorageProvider` pattern as media, exposed via `/account/avatar/*` and `/auth/me`) and a real settings hub (`apps/mobile/app/settings/`, `app/account/profile.tsx`) — previously scattered logout/deactivate buttons on the home screen, now consolidated with device management broken out to its own screen.

A schema gap surfaced and was fixed: the original §4 `messages` table had no column for replies, needed for Phase 4's "replies" feature — added via migration `7cb71e7570d4`. 74 backend tests pass total (18 new messaging-service tests, 8 new API tests). 42 mobile tests pass total (8 new: base64 round-trip correctness, WebSocket event dispatch/subscription with a mocked global `WebSocket`). `docs/SECURITY_GAPS.md` now leads with the libsignal gap as the single highest-priority item in the codebase — it blocks the product's core function, unlike the onboarding-vendor-credential gaps.

**Phase 5 — Circle: complete (backend + real mobile UI).** No native-crypto blocker here, unlike Phase 4 — everything in this phase is real, both ends. `domain/circle/service.py` (`CircleService`) implements §22-24: contact requests (send/accept/decline/list, both sides land at `unverified` tier on send so the pending relationship is visible before either side can message), tier transitions (`unverified` → `verified` on mutual accept → `trusted` via one-sided safety-number confirmation, §23), block/report (moved out of `MessagingService`, which now only reads `BlockRepository` for its own messaging-capability check — block's fuller §24 side effects, hiding the blocker from the blocked user's list and silently dropping any pending request, belong to Circle, not messaging), and invitations (`system_config.invite_only_mode` now actually gates `OnboardingService.start_signup`, redeeming a real `Invitation` row with a `expires_at` — added via migration `6511f2a9f7f2` since the original §4 schema never put a TTL on invite codes despite spec text calling them "time-bounded").

A real cross-phase integration was wired in, not just documented: `MessagingService.start_direct_conversation` now requires a `verified`/`trusted` Circle contact between the two users (§22 — "basic messaging unlocked once both sides accept"), and `MessagingService.register_identity_key` demotes any `trusted` contact back to `verified` (clearing `safety_number_verified_at`) when a device's identity key actually changes vs. an idempotent resend — §23's "does not silently trust re-keyed contacts," now enforced in code, not just spec prose. This touched every Phase 4 test that creates a direct conversation; all were updated to set up a verified `Contact` row first rather than relaxing the new gate.

`GET /auth/me` was added (`CurrentUserResponse`) — a small, real gap: the mobile client had no way to learn its own user id for Circle's add-contact link/QR flow without decoding its own JWT locally.

**Deliberately not built in mobile Phase 5**: an on-screen "safety number" display (two fingerprint strings a user compares to verify a contact). Per the same principle as ADR 0005, fabricating that display without real Signal identity keys would be exactly the "looks encrypted without being any such thing" problem — so `app/circle/index.tsx`'s "Verify in person" action is a real, honest attestation (it really does call `POST /circle/safety-number/verify` and really does promote the contact to `trusted`) with copy that doesn't claim to show a cryptographic fingerprint. Also not built: QR code *generation* (rendering own code as a scannable image) — no QR-generation library was added, to avoid a new native dependency on this memory-constrained dev machine; QR *scanning* (via `expo-camera`) and link-sharing (native `Share` sheet + `expo-linking` deep link, both already-installed dependencies) are real and cover the same `ditsala://circle/add?userId=<id>` flow either way. See `docs/SECURITY_GAPS.md`.

**Phase 6 — Location, SOS, Calls: complete (backend + real mobile UI, including voice/video calling).** `domain/location/service.py` implements §25: `trusted`-tier-only sharing grants, ping recording, and access-transparency logging (every recipient view is logged and surfaced back to the sharer). `domain/sos/service.py` implements §26: trigger → armed → cancel-window → escalate, notifying every `trusted` Circle member (push + SMS) and every `notified_on_sos` next-of-kin row (SMS only — they have no DITSALA account or push token). Two new provider interfaces were added for this, following the same real-adapter-plus-sandbox-adapter pattern as KYC/OTP/Email (Working Rule 4, not in spec §3.4's table but the rule applies generally — `StorageProvider` got the same treatment in Phase 4): `PushProvider` (`ExpoPushProvider` real; `SandboxPushProvider` is a **documented exception** — Expo's push API has no distinct sandbox/test mode the way Twilio/Smile ID do, so the sandbox adapter logs instead of calling a real endpoint, called out explicitly rather than silently) and `SmsProvider` (`TwilioSmsProvider` real; `SandboxSmsProvider` genuinely uses Twilio's test-credential pattern, same as the existing OTP sandbox).

`domain/calls/service.py` implements §27 call signaling: state machine (ringing/active/ended/missed/declined), WebRTC offer/answer/ICE relay over the same realtime WebSocket transport messaging uses, `GET /calls/ice-servers` (STUN + the Phase-0-scaffolded coturn), and **voice<->video switching mid-call** (`switch_media` — either participant, at any point during an active call, not just the one who placed it). Calls are gated to `direct` conversations only (group calls out of v1 scope, settled).

**Mobile ships real WebRTC calling, not plumbing-only** — see `docs/adr/0007-calls-native-module-verification-gap.md` for why this phase's judgment call differs from ADR 0005's: `react-native-webrtc` needed no cryptographic or native binding code written by this session (unlike libsignal), so building against its real, documented API carries none of ADR 0005's "looks encrypted without being any such thing" risk. `lib/call-session.ts` (real `RTCPeerConnection` lifecycle, local/remote stream wiring, mute, and track add/remove + renegotiation for the voice/video switch), `lib/call-context.tsx` (app-wide incoming-call routing, mounted at the root layout like `OnboardingProvider`, using expo-router's imperative `router` export since it renders outside the Stack's own navigation context), and real screens (`app/calls/incoming.tsx`, `app/calls/active.tsx` with actual `RTCView` video) are all real code. `react-native-webrtc` + `@config-plugins/react-native-webrtc` + `expo-location` were added as real dependencies (`app.json` plugin list updated with mic/camera/location permission strings). **Not runtime-verified** — same boundary as everything else mobile since Phase 2, just a heavier native module than expo-camera/expo-local-authentication: no `expo prebuild`, simulator, device, or EAS build exists in this environment. The self-hosted coturn TURN server was also not run locally (Docker not installed, same as Phase 0's other infra).

**Poor-network resilience, addressed directly (explicit user ask this phase):** `lib/api.ts`'s shared `request()` now retries transient failures (no response, or 502/503/504) with backoff and a 15s timeout, never retrying a real 4xx rejection or an ambiguous bare 500. `lib/messaging-ws.ts` (the one long-lived connection — messaging events and call signaling both ride it) now auto-reconnects with exponential backoff on an unexpected close, distinct from an intentional `disconnect()`. SOS specifically gets its own retry layer on top of that (`lib/sos-queue.ts`'s `triggerSosWithRetry`): an emergency trigger keeps retrying every few seconds — by default indefinitely — rather than surfacing a one-shot failure, since this is the one action in the app that must never silently drop on a dead connection.

Also added: `GET /circle/contacts` and Circle's list endpoints now enrich responses with the other party's `display_name` (`ContactWithProfile`/`ContactRequestWithProfiles` in `domain/circle/service.py`) — needed once `app/calls/incoming.tsx` and the Circle screen's call buttons needed a human-readable name, not just a raw user id.

**Phase 8 — Recovery & Hardening: complete.** All of §33 (account recovery), §34.2 (deletion cascade), §32 (rate limiting), scheduled retention/escalation sweeps, §34.4 (data subject rights), and the 6 policy documents (§36) are real, tested code — not narrative.

**Account recovery (§33)**: `domain/recovery/service.py` (`RecoveryService`) implements the full flow — email+phone re-verification, Smile ID SmartSelfie *Authentication* (a 1:1 match against the existing enrollment, never a document re-capture — see `docs/adr/0005`'s zero-retention posture, unchanged here), a next-of-kin attestation window (SMS with a public, token-gated flag link), then session reset via `AuthService.complete_recovery_session` (revokes every existing device/session and issues a fresh one — deliberately reuses the same method Phase 3 already had rather than duplicating session issuance). `AccountRecoveryRequest` gained `email_verified`/`phone_verified` flags (migration `da8348fec0b8`) since liveness must gate on both, not either. Mobile ships real screens (`app/recovery/*`, `lib/recovery-api.ts`, `lib/recovery-context.tsx`), reachable via a new "Forgot your code?" link on the login screen — same native-SDK-gap caveat as onboarding's liveness screen (ADR 0005/0007's reasoning: request the real backend job, but no Smile ID SDK to drive the capture itself in this environment).

**Account lifecycle (§14, §34.2)**: `domain/account/service.py` (`AccountLifecycleService`) implements self-service deactivation with a 30-day reversible grace window (`request_deactivation`/`cancel_deactivation`) and the scheduled hard-delete sweep (`process_scheduled_deletions`). Hard-deleting a `User` is deliberately just one `DELETE` — every one of the 27 `users.id` foreign keys in this schema is `ondelete="CASCADE"`, so Postgres performs the cascade the spec describes; see `docs/adr/0009-account-deletion-cascade.md` for why, and why `audit_log` (no FK to `users`) is the one deliberate exception. Banning a user (`AdminService.action_report`, `KycReviewService.reject`) now also sets `hard_delete_after = now()`, joining the same deletion-cascade code path with no grace period, per §34.2's "banned → immediate soft-delete." Mobile: `app/account/deactivate.tsx`, reachable from the home screen, also doubles as the reactivation screen (signing back in during the grace window still works — nothing in `AuthService.start_login` gates on `account_state` beyond the existing lockout — so cancelling deactivation is just a second button on the same screen after logging back in).

**Rate limiting (§32)**: `domain/ratelimit/interfaces.py` (`RateLimiter` Protocol, `RateLimitExceeded`) + `services/ratelimit/memory.py` (`InMemoryRateLimiter`, fixed-window, single-process) follow the same real-adapter-behind-an-interface pattern as every other provider, with the in-memory adapter documented as the `ConnectionManager`-style single-instance placeholder for a future Redis-backed one. A single FastAPI exception handler (`main.py`) turns any `RateLimitExceeded` into a 429 with `Retry-After`, so no router needs its own try/except for this. Wired into `OnboardingService` (email/phone code sends), `RecoveryService` (recovery start), `AuthService` (per-IP login-start limiting, layered on top of the pre-existing per-account escalating lockout), `CircleService` (contact requests, invitations), and `SosService` (triggers — deliberately generous, 10/hour, since a real emergency can involve several trigger attempts). Per-IP limiting is deliberately *not* applied to invitations/contact-requests/SOS — see `docs/adr/0010-rate-limiting-key-choice.md` for why (carrier-grade NAT is common in this product's target market, and layering per-IP on top of already-authenticated, per-account-identified actions would incidentally throttle unrelated legitimate users sharing that IP).

**Scheduled maintenance (§32, §34.2, §26, §7.3)**: `app/tasks/scheduler.py`, wired into `main.py`'s lifespan via APScheduler's `AsyncIOScheduler` (new dependency) — message-expiry purge, SOS escalation (armed events past their cancel window), location-ping retention, login-attempt/recovery-request 12-month retention, and the account hard-delete sweep, all running in-process on a timer rather than the originally-envisioned Redis-backed queue (no Redis binary in this environment — see `app/tasks/README.md`, same reasoning as `ConnectionManager`/`InMemoryRateLimiter`). Verified with a real `uvicorn` server startup (scheduler starts and shuts down cleanly, confirmed via a live health-check hit), not just unit tests.

**Data subject rights (§34.4)**: new `data_subject_requests` table (migration `436d571ee7d4`) + `domain/compliance/service.py` (`ComplianceService`) — users file access/correction/deletion requests (`POST /account/data-requests`), tracked against a 30-day SLA computed at filing time; admins with a new `data_subject_requests:view`/`:action` permission pair list and action them (`/admin/data-subject-requests/*`). Completing a **deletion** request genuinely delegates to `AccountLifecycleService.request_deactivation` — one deletion-cascade code path, not two. Completing an **access** request does not yet generate an automatic data-export bundle — that's tracked as a real, separate gap in `docs/SECURITY_GAPS.md`, not silently glossed over.

## Security non-negotiables (spec §7 — do not weaken these while implementing)

1. No custom cryptography anywhere — audited primitives only (TweetNaCl for E2EE, per ADR 0013; Argon2id for secrets). "Custom" means the *primitives* (never hand-roll a cipher/hash/signature scheme); composing audited primitives into a protocol (ADR 0013's session-less X3DH-lite) is a design choice, not an instance of this rule, and is itself documented and reviewable.
2. No plaintext DITSALA Codes, tokens, or biometric templates ever stored.
3. **No admin path, ever, can retrieve decrypted message content** — true even for support/law-enforcement scenarios.
4. Every external provider behind an interface with a real adapter + a `Sandbox*` adapter using the provider's own test mode. Selection by env var only — never a hand-rolled fake in a production code path.
5. Every schema change is an Alembic migration. No manual DDL, anywhere, ever.
6. Anything that can't yet be built safely is isolated behind an interface and logged in `docs/SECURITY_GAPS.md`, not shipped with a silent weaker fallback.
7. Secrets only via env vars; `.env.example` (no real values) in every app; `.env*` and key material gitignored (already done, see `.gitignore`).

## Compliance (spec §34 — resolved, not open questions)

- **KYC/biometric imagery: zero retention in DITSALA-controlled storage, ever.** Only `smile_id_job_id` + a non-reversible `result_summary` (scores/decision) are stored. This is a POPIA §14/§26-27 driven decision — don't reintroduce a "store the image with a TTL" pattern without revisiting the spec.
- Cross-border transfers to Smile ID/Twilio/Resend require signed DPAs with SCCs (or equivalent) — **launch blocker for Phase 2**, tracked in `docs/SECURITY_GAPS.md` until each is signed.
- SOS overriding standing location-consent settings is a deliberate, documented lawful-basis exception (POPIA §11(1)(d)), not a gap — don't "fix" it by adding a consent prompt into the SOS escalation path.
- Concrete retention numbers (location pings, audit log, login attempts, account deletion cascade) are fixed in spec §34.2 — `DATA_RETENTION.md` (Phase 8) implements them, doesn't re-derive them.
